# Supported trackers

🇬🇧 English · 🇩🇪 [Deutsch](de/trackers.md)

Your team might use any of 20+ trackers. They differ a lot: some have native dependencies, others none; some push webhooks, others have to be polled; some keep everything in custom fields. This page shows **what each tracker can offer, how far support is, and how agentic-pm copes with what's missing**.

Today GitHub Issues and OpenProject can be read (Phase 1). Every other tracker has a planned issue under the [adapter epic #18](https://github.com/Wieshof/agentic-pm/issues/18).

```bash
uv run agent-pm trackers            # the same list in your terminal
uv run agent-pm trackers --tier 1   # only what's next
```

**Tiers.** 1 = next (widely used, good API fit for dependency-aware PM). 2 = later. 3 = limited fit for team project management, e.g. personal task lists or bug trackers without planning fields. A tier is a suggested order, not a gate: contributions for any tracker are welcome.

## How agentic-pm copes with gaps

Every adapter declares its **capabilities**. The engine uses them instead of guessing, and tells leads what it cannot check, so silence is never mistaken for "all good".

| Missing | What happens |
|---------|--------------|
| Dependencies (—) | No risk propagation. Overdue and due-soon still work. Lead briefs say "Your tracker doesn't provide dependencies". |
| Dependencies via text (📝) | Lines like `Blocked by #12` in the description become edges, where the tracker has stable ids. |
| Dependencies via relation field (🔗) | You name the relation property in `tracker_options` ([#23](https://github.com/Wieshof/agentic-pm/issues/23)). |
| Estimates | Each task counts as 1 day in the schedule. |
| Due dates | The task is listed, but not part of risk calculations. |
| Webhooks (🔄) | Polling compares `updated_at` and feeds the same webhook gate (dedup + self-trigger protection), see [#22](https://github.com/Wieshof/agentic-pm/issues/22). |
| Status categories | A `status_map` in `tracker_options` maps your columns or labels to open / in progress / in review / blocked / done. |

## Configuring a tracker

```yaml
project:
  tracker: jira                 # key from `agent-pm trackers`
  repo: APP                     # project key / repository / board id
  base_url: https://acme.atlassian.net
  tracker_options:              # only for trackers that need a mapping (no secrets!)
    status_map: {"In QA": in_review}
    fields: {estimate: "Story points"}
```

**Secrets** always come from environment variables. The existing adapters use `GITHUB_TOKEN` and `OPENPROJECT_API_KEY`. New adapters follow the pattern `AGENT_PM_<TRACKER>_TOKEN` (plus e.g. `AGENT_PM_JIRA_EMAIL` where the API needs it).

**Least privilege.** In Phase 1 the agent only reads. Give it a dedicated service account or token with **read-only** access to the projects it should see. Write scopes are only needed from Phase 2 on, and then only for comments and labels at first (see [guardrails](guardrails.md)). Put that account's login into `project.agent_accounts` so its own changes never trigger it.

If you pick a tracker that is known but not built yet, the agent says so in a friendly way and links the issue.

## Gitea / Forgejo mapping

Use `tracker: gitea`, `repo: owner/repository` and `base_url: https://forge.example`
(include an installation subpath if needed, but not `/api/v1`). Put the read-only token in
`AGENT_PM_GITEA_TOKEN`. The adapter uses the shared Gitea/Forgejo REST API at `/api/v1`;
it never sends write requests.

Native open/closed issue state maps to `open`/`done`. Open issues may use
`status:in-progress`, `status:in-review` or `status:blocked` labels. Gitea does not
provide a separate cancellation reason, so a closed issue is not guessed to be cancelled.
Native `due_date`, multiple assignees, comments and both dependency directions are read.
Pull requests are excluded. Time tracking is not treated as an estimate, and project-board
columns and sub-issue hierarchies are not inferred.

Webhook consumers must first verify the raw request body using
`agentic_pm.adapters.gitea.verify_signature` and `X-Gitea-Signature` (or
`X-Forgejo-Signature`), then pass the `issues` or `issue_comment` event, JSON payload
and delivery ID to `handle_webhook`. Agent-account, duplicate-delivery and burst filtering
use the shared webhook gate. Live compatibility has not been verified against a private
installation; the adapter is tested offline with an anonymized public Forgejo response.

API references: [issue fields](https://docs.gitea.com/api/operations/issue-get-issue/),
[dependencies](https://docs.gitea.com/api/operations/issue-list-issue-dependencies/) and
[Forgejo webhooks](https://forgejo.org/docs/latest/user/repository/webhooks/).

## Your tracker isn't listed?

1. Open an issue with the tracker's name and API docs. It goes into the catalog as a `candidate`.
2. Or build it as a **plugin** in your own package, without changing this repository:

```toml
# pyproject.toml of your plugin
[project.entry-points."agentic_pm.adapters"]
youtrack = "agentic_pm_youtrack:build"   # build(project, env) -> TrackerAdapter
```

## Adding an adapter (checklist)

Each tracker issue contains this checklist:

1. Verify the catalog row against the current API docs and correct `catalog.yaml` if needed.
2. Write `src/agentic_pm/adapters/<key>.py` implementing `TrackerAdapter`, read-only first. The [GitHub adapter](../src/agentic_pm/adapters/github.py) is the reference.
3. Map statuses, preferring the tracker's own status category or type over names.
4. Write tests with **recorded API responses** and the shared contract suite. CI needs no account.

   ```python
   from agentic_pm.testing import AdapterContract


   class TestJiraContract(AdapterContract):
       project, existing_id, missing_id = "APP", "APP-1", "APP-999"

       async def make(self):
           return JiraAdapter(..., transport=recorded)
   ```

5. Register it in `adapters/registry.py`, set `status: available`, and run `uv run agent-pm trackers --write-docs`. CI fails if the docs are out of date.
6. Add the mapping notes to this page in English and German.

Background: [ADR-0002](adr/0002-tracker-adapter-strategy.md).
