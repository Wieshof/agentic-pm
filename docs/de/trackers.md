# Unterstützte Tracker

🇬🇧 [English](../trackers.md) · 🇩🇪 Deutsch

Dein Team nutzt vielleicht einen von über 20 Trackern. Sie unterscheiden sich stark: Manche haben native Abhängigkeiten, andere gar keine; manche schicken Webhooks, andere müssen abgefragt werden; manche speichern alles in eigenen Feldern. Diese Seite zeigt, **was jeder Tracker liefern kann, wie weit die Unterstützung ist und wie agentic-pm mit Lücken umgeht**.

Heute lassen sich GitHub Issues und OpenProject lesen (Phase 1). Für jeden anderen Tracker gibt es ein geplantes Issue im [Adapter-Epic #18](https://github.com/Wieshof/agentic-pm/issues/18).

```bash
uv run agent-pm trackers            # dieselbe Liste im Terminal
uv run agent-pm trackers --tier 1   # nur das, was als Nächstes kommt
```

## Gitea / Forgejo: Zuordnung

`tracker: gitea`, `repo: besitzer/repository` und `base_url: https://forge.example`
verwenden. Ein Installations-Unterpfad ist möglich; `/api/v1` nicht anhängen.
Das Lesetoken kommt ausschließlich aus `AGENT_PM_GITEA_TOKEN`. Der Adapter liest
die gemeinsame REST-API und sendet keine schreibenden Requests.

Offene/geschlossene Issues werden auf `open`/`done` abgebildet. Für offene Issues
werden die Labels `status:in-progress`, `status:in-review` und `status:blocked` erkannt.
Ein geschlossenes Issue wird nicht ohne entsprechende API-Daten als abgebrochen interpretiert.
`due_date`, mehrere Zuständige, Kommentare und beide Richtungen nativer Abhängigkeiten
werden gelesen. Pull Requests, geschätzte Aufwände und eine vermutete Hierarchie sind ausgeschlossen.

Vor `handle_webhook` müssen Empfänger den unveränderten Request-Body mit
`agentic_pm.adapters.gitea.verify_signature` und `X-Gitea-Signature` bzw.
`X-Forgejo-Signature` prüfen. Anschließend werden Ereignisname (`issues` oder
`issue_comment`), Payload und Delivery-ID übergeben. Das gemeinsame Webhook-Gate
filtert Agentenaktionen, doppelte Zustellungen und Ereignis-Bursts.
Offline-Tests verwenden eine anonymisierte öffentliche Forgejo-Antwort; eine private
Installation wurde nicht live geprüft.

**Stufen.** 1 = als Nächstes (weit verbreitet, API passt gut zu abhängigkeitsbewusstem PM). 2 = später. 3 = passt nur begrenzt zu Team-Projektmanagement, z. B. persönliche Aufgabenlisten oder Bugtracker ohne Planungsfelder. Eine Stufe ist eine vorgeschlagene Reihenfolge, keine Hürde: Beiträge für jeden Tracker sind willkommen.

## Wie agentic-pm mit Lücken umgeht

Jeder Adapter gibt seine **Fähigkeiten** an. Die Engine richtet sich danach, statt zu raten, und sagt Teamleitungen, was sie nicht prüfen kann. So wird Stille nie mit „alles gut“ verwechselt.

| Fehlt | Was passiert |
|-------|--------------|
| Abhängigkeiten (—) | Keine Risiko-Weitergabe. Überfällig und bald fällig funktionieren weiter. Briefings für Teamleitungen sagen „Dein Tracker liefert keine Abhängigkeiten“. |
| Abhängigkeiten per Text (📝) | Zeilen wie `Blocked by #12` in der Beschreibung werden zu Kanten, sofern der Tracker stabile IDs hat. |
| Abhängigkeiten per Beziehungsfeld (🔗) | Du nennst die Beziehungs-Eigenschaft in `tracker_options` ([#23](https://github.com/Wieshof/agentic-pm/issues/23)). |
| Schätzungen | Jede Aufgabe zählt im Zeitplan als 1 Tag. |
| Fälligkeiten | Die Aufgabe wird aufgeführt, fließt aber nicht in die Risikoberechnung ein. |
| Webhooks (🔄) | Polling vergleicht `updated_at` und speist denselben Webhook-Filter (Duplikate + Schutz vor Selbstauslösung), siehe [#22](https://github.com/Wieshof/agentic-pm/issues/22). |
| Status-Kategorien | Eine `status_map` in `tracker_options` ordnet Deine Spalten oder Labels offen / in Arbeit / im Review / blockiert / erledigt zu. |

## Einen Tracker konfigurieren

```yaml
project:
  tracker: jira                 # Schlüssel aus `agent-pm trackers`
  repo: APP                     # Projektschlüssel / Repository / Board-ID
  base_url: https://acme.atlassian.net
  tracker_options:              # nur für Tracker, die eine Zuordnung brauchen (keine Geheimnisse!)
    status_map: {"In QA": in_review}
    fields: {estimate: "Story points"}
```

**Geheimnisse** kommen immer aus Umgebungsvariablen. Die vorhandenen Adapter nutzen `GITHUB_TOKEN` und `OPENPROJECT_API_KEY`. Neue Adapter folgen dem Muster `AGENT_PM_<TRACKER>_TOKEN` (plus z. B. `AGENT_PM_JIRA_EMAIL`, wo die API das braucht).

**Minimale Rechte.** In Phase 1 liest der Agent nur. Gib ihm ein eigenes Service-Konto oder Token mit **nur Lesezugriff** auf die Projekte, die er sehen soll. Schreibrechte braucht er erst ab Phase 2, und dann zunächst nur für Kommentare und Labels (siehe [Leitplanken](guardrails.md)). Trag den Login dieses Kontos in `project.agent_accounts` ein, damit ihn seine eigenen Änderungen nie auslösen.

Wählst Du einen Tracker, der bekannt, aber noch nicht gebaut ist, sagt Dir der Agent das freundlich und verlinkt das Issue.

## Dein Tracker fehlt?

1. Eröffne ein Issue mit dem Namen des Trackers und seiner API-Doku. Er kommt als `candidate` in den Katalog.
2. Oder baue ihn als **Plugin** in Deinem eigenen Paket, ohne dieses Repository zu ändern:

```toml
# pyproject.toml Deines Plugins
[project.entry-points."agentic_pm.adapters"]
youtrack = "agentic_pm_youtrack:build"   # build(project, env) -> TrackerAdapter
```

## Einen Adapter hinzufügen (Checkliste)

Jedes Tracker-Issue enthält diese Checkliste:

1. Prüfe die Katalogzeile gegen die aktuelle API-Doku und korrigiere `catalog.yaml` bei Bedarf.
2. Schreibe `src/agentic_pm/adapters/<key>.py` mit dem `TrackerAdapter`-Protokoll, zuerst nur lesend. Der [GitHub-Adapter](../../src/agentic_pm/adapters/github.py) ist die Vorlage.
3. Bilde die Status ab, bevorzugt über die Status-Kategorie oder den Status-Typ des Trackers statt über Namen.
4. Schreibe Tests mit **aufgezeichneten API-Antworten** und der gemeinsamen Vertrags-Testsuite. CI braucht kein Konto.

   ```python
   from agentic_pm.testing import AdapterContract


   class TestJiraContract(AdapterContract):
       project, existing_id, missing_id = "APP", "APP-1", "APP-999"

       async def make(self):
           return JiraAdapter(..., transport=recorded)
   ```

5. Registriere ihn in `adapters/registry.py`, setze `status: available` und führe `uv run agent-pm trackers --write-docs` aus. CI schlägt fehl, wenn die Doku veraltet ist.
6. Ergänze die Zuordnungshinweise auf dieser Seite, auf Englisch und Deutsch.
